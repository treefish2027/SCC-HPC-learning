# 第三关实验报告
## 1. 代码理解与接口

本任务从日志中筛选符合条件的记录，要求不修改输入，完整保留命中记录的字段、顺序和重复项。

原始 baseline_old.cpp 的 main 同时负责参数解析、输入生成或加载、筛选、校验、计时和输出。其中：

- generate/load：生成或读取输入。
- 核心循环：判断记录是否满足查询，并写入结果。
- reference_filter/equal_record：生成参考答案，检查输出数量、字段和顺序。
- steady_clock：测量核心计算耗时。
- save：按需将结果写入文件。

首先保留原始代码，将串行筛选循环抽取为独立接口：

    std::size_t filter_records(const Record* input, std::size_t count,
                               Record* output, const Query& query);

重构后的文件为 baseline_serial.cpp。本次只移动筛选职责，没有改变串行算法，重构后通过全部 7 项公开测试。

该函数返回命中记录数量，输出缓冲区的前若干条为有效结果。调用方保证输入输出不重叠，输出容量至少为 count，并负责拒绝非法查询。count 为 0 时，函数不访问输入输出指针。

函数内部不读取文件、不生成测试数据、不打印，也不调用参考校验函数。之后在 filter_openmp.cpp 中实现同一接口的并行版本。

## 2. 环境与可复现基线

### 实验环境

- 系统：WSL2，Ubuntu 24.04.5 LTS。
- 内核：6.18.40.1-microsoft-standard-WSL2。
- CPU 型号：Intel Core i5-14600KF。
- WSL 可见逻辑处理器：20 个，不据此推断宿主机物理核心数量。
- 编译器：G++ 13.3.0。
- Python：3.12.3。

完整环境记录保存在 evidence/environment.txt。

### 编译和运行参数

串行版编译命令：

    g++ -std=c++17 baseline_serial.cpp -O2 -o log_filter_serial

并行版编译命令：

    g++ -std=c++17 filter_openmp.cpp -O2 -fopenmp -o log_filter_openmp

串行版使用一个线程。并行测量设置 OMP_NUM_THREADS=20、OMP_DYNAMIC=FALSE。输出中的 threads_max=20 是最大线程数设置，未在并行区域内单独记录实际团队大小。

测试规模分别为 1000000 和 10000000 条记录。共同参数为 seed=2026、pattern=random、hit-percent=50、repeats=5。

查询条件相同：时间范围 [1000,2000)、延迟至少 100、标记包含 3 的全部位。相同规模的两个版本使用相同生成器、seed 和查询参数。

### 计时范围

每次运行先预热一次，再记录五次正式样本，取中位数比较。

计时包围 filter_records 函数调用，包含筛选和输出写入。并行版还包含临时容器创建、扩容、释放、并行区域执行、同步和结果合并。

输入生成或加载、最终输出缓冲区准备、参考校验、控制台打印和文件输出不在核心计时内。

预热可能使后续调用复用 OpenMP 运行时的线程资源，因此这些数据反映预热后的性能，不代表首次启动耗时。

- evidence/openmp_1m.txt

## 3. 热点、假设与选择

### 优化目标与证据

程序需要遍历输入，对每条记录进行条件判断，并写出命中记录，因此选择筛选及输出循环作为优化目标。

目前的证据来自代码分析和核心区域计时，没有使用采样剖析或硬件计数器。因此不能确定这一部分占整个程序运行时间的比例，也不能直接认定瓶颈是内存带宽或分支预测。

### 两个候选方向

方案一：每个线程使用自己的临时结果容器。

将输入分段，各线程分别筛选并保存命中记录，最后按顺序合并。这个方案容易从原有循环改起，但会增加容器分配、扩容、记录复制、串行合并和同步开销。本次实际实现并测试了这一方案。

方案二：分块计数，再计算各块的输出位置。

第一遍统计每块的命中数量，再累加前面各块的数量，确定当前块从输出数组的哪个位置开始写。第二遍各块直接写入自己的输出区域。这样可以避免临时结果容器和最后的逐条合并，但需要额外扫描、计数存储和同步。本次没有实现或测量这一方案。

上述方案比较是在已有 OpenMP 初版之后整理的，不是事前实验记录。

### 可验证的假设

假设：并行扫描节省的时间能够超过临时存储、同步和合并的额外开销；较大的输入规模可能更有利于发挥并行优势。

如果并行耗时中位数不低于串行，就不支持该配置下的加速假设。如果规模扩大后加速比下降，就不支持“规模越大收益越高”的预期。

本次两组并行中位数均有所降低，但加速比从约 1.18 倍下降到约 1.07 倍，因此没有观察到规模扩大带来更高加速比。

## 4. 实现与正确性

### 并行实现和顺序保证

filter_openmp.cpp 使用 OpenMP 并行筛选。每个线程将命中记录放入自己的 vector，避免多个线程同时修改同一个结果容器。

循环明确指定 schedule(static)，不指定块大小，将输入按连续段分配给线程。各线程按段内输入顺序保存结果；并行区域结束后，再按线程编号合并各段结果，从而保持全局输入顺序。

输出计数 matched 只在合并阶段更新。合并开始前，各线程已经完成筛选，避免读取尚未完成的临时结果。

通过完整 Record 赋值保留记录字段，不去除重复项，不修改输入。临时容器会占用额外内存，扩容后的容量也可能大于实际命中数量；这些容器的创建、扩容和释放均纳入本次核心计时。

## 5. 性能与适用条件

### 测量结论

100 万条记录的加速比约为 1.18 倍，1000 万条约为 1.07 倍。本次两组并行耗时中位数均低于串行，但改善有限，扩大规模后没有获得更高的加速比。

1000 万条的并行样本约为 38.62 至 48.80 毫秒，存在明显波动，其中部分样本比串行更慢。因此不能将中位数改善理解为每次运行都会更快。

### 可能影响性能的因素

本方案在并行扫描之外，还增加了以下工作：

- 为线程局部容器分配内存，并在追加记录时可能扩容。
- 命中记录先写入临时容器，再复制到最终输出。
- 最后的合并由单个线程完成。
- 进入并行区域及等待各线程完成需要额外开销。

这些额外工作可能抵消部分并行收益，但本次没有分别测量各部分耗时，不能确定哪一项是主要瓶颈。

缓存、内存带宽、WSL 和宿主机调度、后台任务及运行噪声也可能影响结果，本次没有单独量化这些因素。

### 适用范围与局限

结论仅针对本次机器环境、编译选项、20 线程设置、random 分布、约 50% 命中率，以及 100 万和 1000 万两种规模。

每种配置只进行一组五次正式测量，没有进行多轮独立实验，也没有寻找最优线程数。新增回归测试使用多个线程设置，但用于验证正确性，不能作为这些线程数的性能比较。

本次计时包含并行方案新增的临时存储和合并成本，但不包含输入生成、参考校验和文件读写，因此不能代表完整文件处理流程的加速比。

后续可以比较不同线程数、命中率和分布，或实现分块计数与前缀和方案，检验减少临时结果复制是否值得额外扫描成本。这些属于后续方向，并非本次已完成的实验。

## 6. 复盘

### 工具使用与验证

本项目使用 AI 辅助解释代码、提出修改建议、生成部分重构和测试代码，并协助整理报告。本人在 WSL 中按步骤完成文件整理、代码保存、编译、测试和性能测量，根据实际运行输出反馈问题，保留测试结果和原始耗时。

采用的建议包括：保留原始基线、抽取筛选接口、使用线程局部结果容器、明确静态调度，以及逐条比较输出字段和顺序。

对 AI 建议没有仅凭文字判断是否成功，而是通过编译、查看测试脚本、执行公开测试和新增测试进行核实。部分不准确的指导在实际操作中得到纠正。

### 实际问题与修复

1. 初期修改并行代码时出现大括号位置错误，通过检查代码结构、重新编译和测试修复。
2. 曾将输出字段或源码文件名当成终端命令，出现 command not found，之后区分了命令、文件名和程序输出。
3. 最初将公开测试脚本的缺参提示误解为交互输入提示。阅读脚本后，改用“python3 test_public.py ./可执行文件”，确认测试真正执行并通过。
4. 早期并行版没有抽取独立接口，临时容器创建和释放也在计时之外。后续完成接口抽取，将这些成本纳入计时，并重新采集数据。
5. 没有采用“20 线程就应接近 20 倍加速”的判断，也没有将测试脚本总耗时当作筛选函数耗时。

### 对结果的核实与不足

为避免虚假提升，两个版本使用相同生成参数和查询条件，完整检查输出数量、字段和顺序，并明确计时范围。本报告采用修正计时后的数据，不混用早期测量结果。

本次完成了基本实现与实验流程，但对 OpenMP 调度、内存分配和性能波动的理解仍需继续加强。目前能够确认已执行测试的结果，尚不能准确判断主要性能瓶颈。
